- **NEW — Accepted `HandledBy` concurrency race (Step 9):** a customer message can race with a conversation's first staff (Agent) reply. The condition self-corrects — the next customer message observes the already-committed `Human` state and gets no AI reply. - **NEW — Step 13B (`TicketHub`) session-expiry disconnect is client-cooperative, not server-enforced, and this is currently safe only because the SignalR payload stays minimal.** `TicketHub`'s per-connection timer sends `SessionExpiring` at the authenticated cookie's own `ExpiresUtc` and relies on the client calling `connection.stop()` in response — SignalR's public API has no supported way for a detached background timer to force-abort an arbitrary connection from outside an active Hub method invocation, so a non-cooperative or frozen client can technically remain connected and keep receiving `TicketEvent` messages past the cookie's expiry. This is safe today, independently verified, because: (1) the `TicketEvent` payload is exactly `{TicketId, EventType}` — no ticket state, Summary, CustomerId, ConversationId, Priority, Status, SLA data, or staff identity is ever put on the wire; (2) every REST endpoint (`GET /api/tickets`, `GET /api/tickets/{id}`, every mutation) independently re-validates the same cookie and correctly returns 401 once it has expired, confirmed by direct testing against `TicketsController`, regardless of whatever state the SignalR connection is in; so a stale connection's invalidation signal cannot actually be exchanged for any protected ticket data or authenticated functionality — the residual exposure is limited to an opaque ticket identifier plus an event-type/activity signal for that one tenant. This is **not** a claim that the mechanism is permanently safe regardless of what `TicketHub` ever sends. If any future event type on this hub adds ticket state, customer information, staff identity, PII, SLA information, or any other materially useful protected data to the payload — or if a future hub is built with a different payload or threat model — this acceptance must be re-evaluated on its own terms, not assumed to carry over. Closing the gap itself (periodic re-validation, per-connection expiry tracking, etc.) was deliberately not built now since it would reintroduce the kind of persistent/tracked connection state this design otherwise avoids; a future small follow-up could revisit it if the payload's scope ever grows.
- **NEW — OPERATIONAL DEPENDENCY, not a code defect — Step 18 (`Integration` OAuth framework) requires the `DataProtectionKeys` table to be included in the production database backup scope before any real integration is ever connected.** Step 18 persists the ASP.NET Core Data Protection key ring in Postgres (`AddDataProtection().PersistKeysToDbContext<AppDbContext>()`, `backend/Program.cs`) rather than the framework's filesystem default, specifically because the deployment target is still undecided (see `NIVORA_DEVELOPMENT_PLAN_V2.md`) and a filesystem key ring would not durably survive a restart/scale-out on most hosting platforms. `Integration.EncryptedAccessToken`/`EncryptedRefreshToken` are encrypted under keys drawn from this ring via `IIntegrationTokenProtector`. **Consequence, stated precisely: losing the `DataProtectionKeys` table (or its contents) permanently prevents decryption of every already-stored `Integration` access/refresh token — there is no recovery path other than every affected business reconnecting the integration from scratch.** This is a backup/ops checklist item to close out before Shopify (Step 19) goes live in production, not something further code can fix. Separately, `IIntegrationTokenProtector`'s per-platform purpose string (`"Nivora.Integration.{Platform}"`) provides cryptographic purpose separation only — it prevents ciphertext produced for one platform's purpose from being unintentionally decrypted through a different platform's purpose string. It is **not** blast-radius containment: a compromise of the underlying Data Protection key ring itself lets an attacker derive any platform's purpose-specific key and decrypt every `Integration` row across every platform and every tenant. Do not describe purpose strings as limiting the impact of a key-ring compromise.
